# Acceptance for 1.0 readiness

SGD must let another developer preserve explicit structural requirements through real application changes without repeated intervention from the authors. GitHub recognition is an aspiration. Stars, test counts, and a demonstration do not establish this outcome.

The [Parangsae production goal](production-goal.md) remains the application-maintenance acceptance case. External adoption is separate evidence for public usability. Do not claim feedback or sustained use that has not occurred.

## Start from responsibilities

For each feature or defect, identify the enclosing requirement, responsible owners, participating lifecycles, and affected model and code bindings. Include required relationships between those parts. A supported leaf does not establish an unsupported enclosing obligation.

Keep model validity, generated enforcement, native integration, composition, and external effects as separate claims. Missing or unsupported required evidence must remain visible. Do not remove requirements or bindings to obtain a successful result.

## Acceptance gates

| Gate | Required evidence | Current limitation |
| --- | --- | --- |
| Requirement preservation | An independently selected baseline and accepted requirement changes distinguish repairs from policy changes. Deleted obligations, weakened properties, and missing bindings fail. | Supplied-baseline v3/v4 comparison exists. Independent baseline selection and complete native closure are not established. |
| Native enforcement | Actual authoritative values use generated ownership. Permitted behavior succeeds; original failure classes and supported bypasses fail. | The report-custody pilot supplies one scoped case. General application-wide enforcement is not established. |
| Sustainable maintenance | Feature additions, authorized requirement changes, and defect fixes complete through actual installed plugins and CI without generated-source edits or recurring author rescue. | One application defect cycle and earlier scoped trials do not establish all three repeatable workflows. |
| First use | A developer can install the supported package, identify its serving version, reproduce a permitted and refused operation, and understand missing prerequisites. | Copied-runtime validation does not establish a fresh user's installed-agent experience. |
| Explainable failure | Results identify the violated requirement, observed path, relevant native boundary, and missing guarantees. Pele distinguishes checked relationships from display-only links. | Some diagnostics and full-state views exist. Complete root-to-code explanations remain incomplete. |
| Stable public contract | Define compatibility for project schemas, CLI/MCP responses, diagnostics, and generated APIs. Verify the documented upgrade path. | Alpha interfaces and native delivery still need a declared stable compatibility contract. |
| Public usability | Independent maintainers perform representative changes and report setup, false refusals, missed violations, maintenance effort, and required assistance. | No general external-adoption result is established. |

Every gate requires a review of its actual evidence. A passing neighboring test, a compiler-generated expectation, or an author's claim cannot replace the required observation.

## First independently reproducible unit

Use the [retained-operation walkthrough](../examples/retained-operation/README.md). It must connect an enclosing result-preservation obligation to a concrete generated boundary and show:

1. An error-only implementation actually loses the original result and fails an independent preservation check.
2. Generated TypeScript 7 and Rust consumers retain the original payload and distinguish execution, ledger, and report outcomes.
3. A controlled model admission change changes native behavior after regeneration while the consumer sources stay unchanged.
4. Logs, model inputs, generated outputs, and visualizations remain available for inspection.
5. The result states that this is a synthetic reproduction of the real failure class, not a full Parangsae replay or a proof of enclosing-model refinement.

Completing this unit establishes only the demonstration. It does not complete 1.0 readiness or the production goal.

## Compare the additional value

Use a strong comparison: good native types, review, and regression/property tests. Keep requirements, starting code, acceptance criteria, agent configuration, and resources comparable. Record the initial implementation and subsequent maintenance separately.

Measure missed violations, benign changes rejected, elapsed work, model/binding maintenance, and author intervention. Preserve unsuccessful attempts. Do not classify a requirement weakened to fit an implementation as a successful repair.

The current hypothesis is that generated structural contracts reduce maintenance cost and preserve important responsibilities across changes. If their costs exceed their benefits in representative projects, revise the scope or design before expanding it.

Contacting external maintainers, publishing outreach, or changing another project's requirements needs the user's authorization. Preparing a self-contained experiment and invitation does not establish external participation.
