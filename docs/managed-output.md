# Managed output and interrupted generation

Use an empty output directory for the first generation. Keep `.sgd-generated.json`; inventory v1 remains compatible with existing generated projects. Later generation updates owned files, removes obsolete owned files, and preserves unrelated files. It refuses to overwrite a file that the previous inventory does not own.

The compiler records exact before/after bytes and inventory membership in `.sgd-transaction.json` before changing managed paths. Files are staged and renamed individually. The inventory is published after those files. A cooperating generator holds the output's exclusive lease throughout this operation.

## Recover a terminated generator

Rerun generation without `--check`. On Linux or macOS, the compiler compares host, boot, process namespace, PID, and process start identity. Only a verified inactive owner permits automatic takeover. A changed PID start identity detects PID reuse; elapsed time alone never expires an owner.

Recovery first checks every recorded path. Each must match its recorded before or after state. An edited file, symlink, unrelated lock entry, or unrecognized inventory stops recovery and preserves the conflicting data. Restore the reported recorded version after inspecting it, or select a separate output directory. A successful recovery finishes the interrupted generation before processing the newly requested file set; the old generator is not required.

`--check` never replays a journal or repairs an incomplete managed generation. It reports `TLC104`. Ordinary checks still compare the complete owned file set, stable generated bytes, and selected stable receipt fields.

## Explain stale output

A completed output comparison that fails with `TLC104` reports all differing artifacts. The CLI keeps its nonzero exit and JSON `error` string. MCP keeps `isError: true` and its JSON text `error`. Both add a `diagnostic` object with schema `sgd-stale-output-v1`.

The diagnostic contains the following fields:

| Field | Meaning |
| --- | --- |
| `differences` | Added or removed inventory entries, missing files, changed content, changed stable receipt fields, and malformed previous receipts. |
| `sourceInventories` | Changed recorded application paths or model module names, grouped by generated artifact and JSON field. Known row plans and controlled receipts supply these inventories. Arbitrary path metadata is not treated as source evidence. |
| `generatedSources` | Byte comparisons for generated TypeScript and JavaScript source. Additions, removals, missing files, changes, and unchanged files remain separate. |
| `nextAction` | Review the differences, then explicitly rerun generation without `--check`. The failed check updates no generated files. |

For example, a collector implementation change can report `src/run.rs` in the affected row plans and verification receipts while generated source bytes remain `unchanged`. A malformed, duplicate, or missing previous inventory reports `previous-unavailable` instead of guessing which source changed. Model module names remain scoped to their receipt field because different referenced contracts can use the same name. The diagnostic does not include source content or digest values, and it never reads files through recorded source paths.

Generated source byte equality does not establish semantic equivalence. A changed model, binding, output set, or other artifact still fails the check. The diagnostic does not authorize a receipt-only refresh, omit a source from freshness checks, or repair generated policy. An explicit generation still uses the existing publication and input-recheck rules.

JavaScript API consumers can catch `StaleOutputError` exported from `dist/compiler.js` and inspect its `diagnostic`. `StaleOutputDiagnosticSchema` validates the serialized report. Lock, journal, symlink, input-verification, and invalid inventory failures can stop before output comparison and retain their existing diagnostics.

## Inspect a controlled TLC failure

In the source checkout, failures represented by `TlcFailureError` in the controlled runner or executable-graph validation add a `diagnostic` with schema `sgd-tlc-failure-v1`. Other configuration, input, and environment errors retain their existing responses. CLI commands keep the JSON `error: string` field on stderr and exit with code `2`. MCP calls keep the JSON text `error` field and `isError: true`. The diagnostic adds the following fields:

| Field | Meaning |
| --- | --- |
| `failure.kind` | `invariant_violation`, `action_property_violation`, `timeout`, `parse_error`, or `unknown`, selected from the evidence below. |
| `failure.phase` | The failed SANY, XML, TLC, source-admission, or executable-graph stage. |
| `failure.invariant` | The configured invariant name, present only for a classified invariant violation. |
| `failure.property` | The configured `PROPERTIES` name, present only for a classified action-property violation. |
| `failure.evidence` | The pinned message code, recognized SANY summary, or owned deadline. Unknown failures have no classified evidence. |
| `counterexample.status` | `not-retained`. The runner removes its private snapshot after success or failure. |
| `nextAction` | A short review or correction step based on the classified kind. |

An invariant violation requires a complete pinned TLC error frame with code `2107` or `2110` and a name from the current `INVARIANTS`. An action-property violation requires code `2112` and an exact name from the current `PROPERTIES`. Evaluation failures such as `2111` or `2113`, general temporal or liveness failures, and property aliases reported under an internal state-predicate name remain `unknown`. A timeout requires the runner's own deadline to expire. Recognized SANY syntax or semantic errors, or pinned TLC parsing messages, support `parse_error`. Within these typed boundaries, external termination, spawn failure, output limits, malformed messages, unsupported source constructs, and ambiguous executable graphs also remain `unknown`.

For an invariant or action-property violation, `nextAction` directs the caller to compare the property and modeled behavior with the accepted requirement and correct the structural cause without weakening the property to obtain a pass. Timeout guidance preserves the required properties and verification scope while the caller investigates model bounds and runner limits.

The runner keeps its error text and bounded output tail, but controlled TLC now uses framed `-tool` output. Raw log text and console prefixes such as `Error: Invariant` are not a compatibility contract. Callers must use the structured failure kind and exact invariant or property name rather than matching those prefixes. Stable diagnostic IDs, CLI exit status, and MCP `isError` remain available.

A complete failure log and a counterexample file are not retained, and the diagnostic exposes no `tracePath`. JavaScript callers can import `TlcFailureError` and `TlcFailureDiagnosticSchema` from `dist/tlc-failure.js`. When a subprocess error exists, it remains available as `cause`. The v1 runner accepts arbitrary JARs and does not use this controlled classification.

Classification does not authorize generation. Successful generation still requires normal process completion, an empty queue, no error or warning, stable inputs, a valid graph, and managed publication. Check-only runs retain their existing comparison behavior without publishing generated files. Fresh failure-log export and retained counterexamples remain separate work.

## Manual cases and limits

- A live owner refuses concurrent generation. Use a separate output directory.
- Empty locks, incomplete owner metadata, unavailable process identity, different host/boot/namespace, and unsupported platforms require manual inspection. Do not delete a lock based on age.
- Termination between lease-directory creation and owner metadata publication leaves a manual case. That owner has not published any generated file at that point.
- Cleanup removes only the recorded control files and empty directories. Edited or unrelated retirement data is preserved for inspection.

The contract covers process-termination recovery on a trusted local filesystem with cooperating generators. Arbitrary readers can observe intermediate per-file publication. This is not an atomic snapshot of the entire output set, hardware power-loss durability, protection against non-cooperating filesystem races, or crash recovery for application data.

Native tests terminate actual publication processes, recover first creation and upgrades, exercise concurrent takeover, and check edited/unrelated-file and symlink preservation. Independent review reproduced and corrected a POSIX literal-backslash symlink escape and a parent-directory permission regression. These cases do not cover every possible I/O interruption.
