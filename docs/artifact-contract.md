# Generated artifact ownership and canonical bytes

Rust generation and freshness checking use one common artifact preparation step. A raw backend emission is a draft. Publication and `--check` accept an immutable prepared batch.

`ArtifactFile` declares one of three roles:

- `compiler-output` declares Rust syntax or verbatim compiler output.
- `captured-evidence` preserves captured bytes, including a captured file with a `.rs` extension.
- `formatter-receipt` binds an existing JSON receipt to the formatter evidence obtained by this preparation.

The public synchronous `compile()` and backend functions still return drafts. `compileProject()`, `buildProject()`, and `writeGenerated()` prepare those drafts before checking or publishing them. The internal `writePreparedGenerated()` rejects objects that the preparation module did not register, including objects made through a reflected constructor.

## Formatter authority

Every compiler-owned Rust unit uses the existing `rustfmt-2021-v1` profile:

```toml
edition = "2021"
style_edition = "2021"
newline_style = "Unix"
```

The compiler runs rustfmt with this explicit configuration in a temporary directory. It formats each unit, compares the actual second formatting pass with the first, and runs rustfmt's check mode. A failure prevents publication and freshness comparison. It removes the temporary directory after success or failure.

The compiler emits the same `rustfmt.toml` beside each generated Rust crate manifest. A Rust unit without a generated manifest receives the configuration in its own directory. An existing conflicting generated configuration is refused.

`artifact-format.json` lists the formatted Rust paths and records the stable profile and configuration identity. The formatter installation version remains informational. Existing v5 row and v6 partition receipts retain the same distinction. Freshness still compares the actual generated Rust bytes; it does not normalize an edited output before comparing it.

A generator-owned profile keeps standalone generation independent of application discovery and preserves the existing v5 contract. A consumer-owned profile would require capturing and rechecking each application's edition and formatter configuration. It would also make older standalone project formats application-bound. The common generator-owned profile therefore defines the generated bytes.

A generated crate's configuration controls standalone formatting. An adapter included through an application's `#[path]` module can be formatted in that application's formatter session. Agreement with that session requires a compatible consumer profile. The real consumer tests use edition 2021 and its default style, include row and partition adapters, and run `cargo fmt --all -- --check`. They do not establish compatibility with every custom consumer formatter configuration.

## Publication order

The common pipeline collects drafts, prepares canonical compiler output, and fills formatter receipts before it freezes the resulting records, stable JSON key lists, and file array. Only the preparation function registers the batch as prepared after its real checks complete.

`buildProject()` then repeats its existing project, original model, source binding, and physical output path checks. The existing managed output transaction consumes the prepared bytes. It retains its ownership, symlink, concurrent writer, recovery, and refusal behavior. Formatter preparation does not replace those checks.

Captured DOT, SANY XML, oracle output, and logs remain unchanged. Their identities continue to refer to the captured evidence, not to a formatted reconstruction. Canonicalizing compiler-owned Rust establishes no new model authority, source coverage, application binding, or effect permission.

## Finite lifecycle model

[`ArtifactLifecycle.tla`](contracts/ArtifactLifecycle.tla) models one compiler-owned Rust unit, one captured evidence unit, two representative Rust byte values, and an original or changed input. Its good configuration checks these invariants:

- Captured evidence retains its original bytes.
- Published Rust is canonical and equals the bytes selected for freshness comparison.
- A ready publication follows the abstract formatter check.
- Refusal publishes nothing.
- Publication uses the rechecked input.

`ArtifactLifecycleBadOrder.cfg` permits selecting freshness bytes before normalization. TLC finds `HashEarly`, `NormalizeOwned`, `CheckOwned`, `Seal`, `RecheckInputs`, then `Publish`, which violates `CanonicalPublished`. `ArtifactLifecycleBadOwnership.cfg` permits normalizing captured evidence and violates `EvidencePreserved` immediately. The good configuration excludes those actions and passes its invariants.

Run each configuration serially with the pinned JAR, one worker, and a separate temporary metadir:

```sh
java -Xmx512m -cp "$TLA2TOOLS_JAR" tlc2.TLC -workers 1 \
  -metadir /tmp/sgd-artifact-good \
  -config docs/contracts/ArtifactLifecycleGood.cfg \
  docs/contracts/ArtifactLifecycle.tla
```

Replace `Good` and the metadir for each bad configuration. The bad configurations must fail with their named invariant violation. The model checks finite ordering and ownership. It does not prove rustfmt, JavaScript reflection, process behavior, or filesystem transactions. Native formatter checks, output preservation tests, and source rechecks establish those implementation boundaries separately.
